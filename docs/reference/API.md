# Manzil API

The Express API shares strict domain contracts between standalone, emulator and production modes. This reference describes the current code; deployed release/configuration state belongs in [implementation status](../IMPLEMENTATION_STATUS.md) and [environment setup](../operations/CONFIGURATION.md).

- Domain and GeoJSON coordinates: **[longitude, latitude]**. API times: ISO instants with explicit offset, normalized to UTC. UI schedules: **Asia/Karachi**.
- Published approved restrictions alone affect public routing. Human moderation and private Gemini review are separate; **clear validated agent changes publish automatically; unresolved changes require administrator approval**.
- Public driving/search covers Pakistan. Closure geometry has no Islamabad city gate, but uses bounded real-road source requests. Bus data remains Twin Cities and weather remains Islamabad.
- Prefer the [closure workflow](../guides/CLOSURE_WORKFLOW.md), [road-source limits](ROAD_COVERAGE.md), [transit reference](TRANSIT_ROUTING.md), [fare reference](TRANSIT_FARES.md) and [administrator workspace](../guides/ADMIN_WORKSPACE.md) for focused details.

## Runtime and identity

The shared Express API supports three explicit modes. Standalone `local` binds to **127.0.0.1:3001**, retains shared SQLite/trusted-local behavior and must not be exposed publicly. `emulator` uses loopback Auth/Firestore and real token/ownership checks. The core `production` API is deployed through **https://manzil-app-v1.web.app/api/** and Cloud Run in Singapore. Hosts/HTTPS origins are explicitly configured; Hosting `fh-*` tagged URLs are accepted only for the selected service. See [environment configuration](../operations/CONFIGURATION.md) and [release procedure](../operations/DEPLOYMENT.md).

In Firebase modes send `Authorization: Bearer FIREBASE_ID_TOKEN` for personal endpoints (commutes/trips/alerts/inference and profile changes) and closure writes. An ordinary signed-in user may submit a report; publication and review follow the role rules below. Admin directory access, demo mutations, notice/outbox access and source changes require a verified token and a **current Auth account** with custom claim `admin: true`; the default verifier reads current account claims rather than trusting an old token's embedded administrator flag. Invalid tokens return 401; insufficient roles return 403. Supplied owner IDs/roles are never authority. Public state contains approved published closures and empty personal lists for guests; private data is scoped to the verified UID. Raw notices are admin-only. Guest appearance is stored in the browser. Speech synthesis requires identity unless explicitly enabled for guests; enabled speech still observes the global application character budget. Direct browser Firestore access is denied by rules.

Registration, Forgot password and `/account/action` use the configured Firebase client Authentication SDK, not new Express endpoints. The branded action page verifies the one-time reset code before password submission; production template URLs require separate release configuration. Disposable emulator tests establish reset-code acceptance/single use and changed-password sign-in, not real mailbox delivery. See [password recovery](../guides/AUTH_PASSWORD_RESET.md) and [entry/auth behavior](../guides/ENTRY_SCREEN.md).

## Community permissions

| Actor | Closure access | Reporting/review | Other access |
| --- | --- | --- | --- |
| Guest | Published, approved closures (legacy published records without moderation remain readable) | Sign-in required for any closure mutation | Public map, planning, search and road-section geometry helper; no personal history |
| Ordinary member | Public closures and their own reports | New/edited reports are forced to `draft` + `moderation: pending`, regardless of requested publication; can edit/cancel their own pending report | Their own saved journeys, alerts, profile and consented trips |
| Verified contributor | Public closures, their own records and pending reports | Can publish their own reports, edit/cancel their own records and other pending/approved-public reports, and approve/reject pending drafts; pending edits remain pending until explicit review | Own personal data; no user directory or source management |
| Admin | All closure records | Can publish, review, edit and cancel closures | Directory, contributor verification and administrator grants/revocations, demo controls and source pipeline. Directory exposes only a minimal name/city/consent projection, never another person's GPS/trips/vehicle; commuter screens are omitted from the admin UI |

Admin authority comes from the currently enabled Firebase Auth account's administrator claim, after token verification. Contributor verification is separate server-owned metadata (`community:member:<uid>`) read for each request; it is not a browser setting or an admin claim. The admin user-management API accepts one contributor-verification change **or** one administrator-role change per request. Administrator changes preserve unrelated custom claims; removal deletes only `admin`, retaining any separately granted contributor verification. Self-demotion and promotion/verification of disabled accounts return 409. A fresh acting administrator is checked again immediately before each serialized role write. Serialization is per API process, not a distributed Auth/Firestore transaction; it does not guarantee a last-administrator invariant across independently running instances. `AppState.membership` supplies the current UID/role/verified flag; the UI only trusts it when its UID matches the current account. Standalone mode deliberately uses one trusted `local-admin` API identity and shared SQLite data; its dummy normal/admin UI accounts cannot test production authorization. Use emulators for permission/isolation checks.

## Local public transport

`GET /api/transit/network?at=ISO`, `GET /api/transit/revision` and strict `POST /api/transit/plan` (`{origin,destination,departureAt}`) are public. The network includes attributed routes/directions/ordered stop records, supplied shapes, mapped corridors or inferred road alignments, active-time uncertainty/suspension statuses and explicit source limitations; it omits bulk trips, private profiles and raw GPS. The current `-roads-8d109199` snapshot has 49 road-aligned estimates, 14 supplied shapes and four mapped Orange directions, preserving 20 explicit missing stop-pair sections. Bus strokes are solid; raw stop-only chords are not drawn. Plans contain bounded walk/ride/transfer legs, known schedule estimates or null unknown times. They enforce service calendars, source/unresolved road gaps, access/boarding restrictions and timed road/service conflicts, then recheck both event and service-notice revisions. Walking connectors remain labelled straight-line estimates. Journey and ride-leg fare metadata provide dated adult per-boarding references; complete/partial/unknown totals never treat an unknown fare as free. [Fare fields and provenance](TRANSIT_FARES.md).

Pattern metadata distinguishes `geometryQuality: provided-shape | mapped-corridor | road-aligned-estimate | stops-only`. Inferred patterns retain `geometrySourceId`, `roadAlignment` (method, per-stop snap distances and unresolved pair indexes/reasons), `breakAfterStopIndexes` and separate `geometrySegments` where needed. The public map omits backend `roadSegments`/`stopDistancesMeters`; plan ride legs contain the actual sliced geometry. Gzip negotiation applies only to `GET /api/transit/network`: missing negotiation or accepted identity returns ordinary JSON; `gzip;q=0` is respected, and excluding both supported encodings returns `406`. Both encodings preserve JSON UTF-8, no-store, existing Origin variation and correct wire-body length.

`GET /api/transit/disruptions` exposes published service notices. Verified contributors/admins can `POST` a validated route/direction/optional ordered section and time window; `PUT /api/transit/disruptions/:id` requires the complete draft plus current `revision` and allows verified reviewers/admins to edit or cancel. Author/role/IDs are server-owned; ordinary users/guests cannot publish. SQLite/Firestore writes are atomic. Source/Gemini service reports prepare separate private proposals; only administrator review publishes them into this same service store, without creating artificial car-road closures. Manual corrections preserve an agent override. See [source proposal review](../operations/AGENT_TRANSIT_REVIEW.md), [full transit contract](TRANSIT_ROUTING.md) and [source/refresh guide](../data-sources/TRANSIT_DATA.md).

Network routes may include `officialReview: {checkedAt,status,summary,references:[{label,url}]}`. Status is `consistent`, `differences`, `reference-only` or `not-established`, limited to the stated fields; it is not an operational verification badge. A pattern's optional `routingUnavailableReason` preserves an explicit source conflict: the network shows uncertainty and the planner excludes that pattern without inventing an operator suspension. The final dataset version includes both the comparison-manifest and road-alignment derivative hashes. Profile Terms/Privacy are static read-only UI documents; opening them grants no permission and adds no account/deletion endpoint.

## Islamabad hourly weather

Public **`GET /api/weather?at=<ISO instant>`** returns the city-level `WeatherResponse` for the matching hour; omitted `at` uses now. Offsets are normalized to UTC and scheduling remains PKT. Unknown query parameters, timezone-free dates and repeated values are rejected. The endpoint accepts no coordinates/city/provider URL. `state` is `fresh`, `stale` or `unavailable`; a nullable `reading` includes hour, temperatureC, WMO weatherCode, isDay, fixed Islamabad coordinate and source/retrieval metadata. `availableUntil` is exclusive. Weather requests share a durable hourly cache and do not change closure/access/route validation.

`POST /api/trips` can attach optional **server-owned `weather`** from fresh cached departure-hour data for trips starting within 30 km of Islamabad; client weather is rejected by the strict input schema. No upstream request is made during trip creation. Existing consent/UID checks still apply. Old/out-of-city/uncovered trips stay without weather and sharing never backfills current values. See [full weather API/cache/provider limits](WEATHER.md).

## Vehicle, fuel prices and spending estimates

`PATCH /api/profile` also accepts `vehicle: {kind:'car'|'motorcycle', label?:string, fuelType:'petrol'|'diesel', kmPerLitre:number|null}`. Economy is finite, 1–200 km/litre, or null to disable estimates. The server manages `vehicleUpdatedAt`; clients cannot backdate it. Optional fields preserve existing profiles. `transport:'car'` continues to describe road routing; vehicle kind changes fuel estimates without enabling motorcycle-specific access/ETAs.

| Method and path | Access | Response |
| --- | --- | --- |
| `GET /api/fuel/prices` | Public | Cached `FuelPriceStatus`: state, last check/success/next daily date, message and dated PSO petrol/diesel records. No external request is triggered. `/state` includes the same object as `fuel`. |
| `POST /api/fuel/check` with `{}` | Admin | Bounded source check or the existing result if attempted in this 01:00-PKT daily cycle. Scheduled execution uses the private worker; no arbitrary source URL or client-supplied prices are accepted. |
| `GET /api/trips/statistics` | Signed-in personal | `{week,month,all}` aggregates over up to 5,000 private retained summaries, independent of the latest-50 display list. Includes distance/time, estimated PKR/litres, priced/unpriced counts, unpriced distance and `complete`. Week/month responses also include private `daily` aggregate series for charts. |

Periods use Monday-start weeks and calendar months in Asia/Karachi, grouped by trip departure. Profile presents **weekly and monthly** statistics, a daily distance chart and a separate cached PSO fuel-price trend. Activity presents the same week/month trip, distance, time and estimated-cost summary cards without graphs. `all` remains available as retained history (up to 90 days); `complete:false` identifies the bounded partial result. No raw points are read or returned for these aggregates. Trips starting or ending after the evaluation instant are excluded.

`week.daily` and `month.daily` contain ascending PKT calendar-date buckets from the period start through today (at most seven and 31 entries). Each bucket has `date` (`YYYY-MM-DD`), `tripCount`, `distanceMeters`, `durationSeconds`, `pricedTripCount`, `unpricedTripCount`, `costPkr` and `litres`. Quiet days have zero totals. Distance/time include all selected summaries; cost/litres include only immutable saved fuel estimates. A trip spanning midnight belongs to its departure date, while its stored fuel estimate may already contain multiple effective-date prices. The current profile or today's quote never reprices history. The same summary safety bound and `complete` flag apply to the daily series. `all` omits `daily`; the field is optional in shared types for older-response compatibility, and the UI shows charts as unavailable when the series is missing rather than inventing daily values from an overall total.

The fuel-price graph uses public cached `fuel.records` from `/state`, not private trip consumption or fictional sample-account rates. It switches Petrol/Diesel and draws a step only at each published `effectiveFrom`, carrying a known earlier price flat into the selected period. It excludes publications effective after the aggregate evaluation time and leaves the interval before the earliest known price uncovered. It neither creates daily price revisions nor triggers a source request; no new API endpoint is added. Exact dated values, PSO source attribution, compact cached-state labels and unavailable history remain available. A stale/error cache is still a dated reference rather than a claim of a successful current check.

New trip records may include server-calculated `fuelEstimate`: estimated PKR, litres, measured accepted distance, the configured vehicle/economy snapshot and dated rate/source/retrieval provenance. Accepted GPS segments crossing an effective date are split by elapsed time. A trip predating the configured vehicle, spanning a vehicle change, outside known price coverage or ending on a day not yet covered by a successful price check remains unpriced. Old estimates are immutable across vehicle/price updates. Consent and current vehicle are rechecked atomically by both adapters. Client-supplied estimates/configuration timestamps cannot manufacture historical spending.

These are **reference estimates, not receipts**. PSO prices exclude outlet freight; future route costs use the latest known applicable quote. Fetch failures/stale cache remain visible. A local running scheduler checks once per PKT date; production needs the separately released worker/Scheduler. See [source parsing, coverage and exact contracts](FUEL_COSTS.md).

## Common request and response rules

`GET /api/runtime` returns public mode/project/auth/storage/scheduling identifiers; the frontend checks these before using the backend. The ordinary API health endpoint is `GET /api/health`. `GET /healthz` belongs to the separately configured private worker, which also accepts authenticated `POST /internal/tick`. The ordinary API returns 404 for worker operations. Worker mode returns 404 for personal API routes. Cloud writes/checks complete before HTTP success; no API timers or untracked post-response work are relied on.

Responses are the domain objects in [`shared/types.ts`](../../shared/types.ts), without an envelope. All coordinates are `[longitude, latitude]`. Send `Content-Type: application/json` for every POST, PUT, or PATCH, including an empty `{}` for check operations. API times are ISO 8601 instants with an offset; responses normalize supplied instants to UTC. Commute wall-clock times and weekdays use Pakistan Standard Time, UTC+05:00.

`PlanRequest` and `CommuteDraft` accept optional ordered `waypoints: Place[]`, at most five. Route paths include `snappedWaypoints` for a journey with stops. Every route option retains stop order, timing and turn restrictions. `PlanResponse.upcoming` lists future closures intersecting the original baseline within 24 hours, independently of `conflicts` (actual traversal overlap). It does not declare a currently open road blocked.

## Closure geometry and display

Road-section selection projects both clicked coordinates within 45 m of supported public car roads and finds a connected portion with the same normalized road name (or OSM way identity for unnamed/generic roads). It is bounded to 3 m–6 km, 400 points and finite search work; failed/ambiguous/disconnected selections return an explicit error. The first point can preview a short approximately 20 m interval, following bends and stopping at connected junctions. A blockade instead retains one short **transverse** line across the affected mapped road, with exactly two endpoints and a 4 m buffer width. It does not close the road between two distant blockade locations: report each physical barrier separately, leaving intermediate sections available through valid intersections. Parallel/collinear strokes, lengths outside 2–80 m and lines not crossing supported public roads return 422. Both endpoints must be within 45 m of the crossed road segment.

All three helpers produce **closure geometry**, not a legal driving itinerary, and save nothing. The imported graph is an offline fast path; outside its bounds, a bounded public OSM road query supplies the selected neighbourhood. There is no Islamabad city gate and no off-road geometry fallback. Unavailable/incomplete external road data returns 503, while unsuitable selections return 422. Resource/length bounds remain. The graph represents car-road/carriageway centerlines, not individual lane geometry or live lane counts. A 2D footprint can conservatively affect overlapping flyovers or both travel directions where they share a centerline. See [workflow and agent contracts](../guides/CLOSURE_WORKFLOW.md), [provider/privacy/budgets](ROAD_COVERAGE.md).

`ClosureDraft.restrictionType` is optional for old records/imports. For a supplied `road_closure` or `blockade`, `drawing` is required and `geometry` must exactly equal the canonical polygon produced from that drawing by `/geometry`. A blockade additionally requires `drawing.kind: line`, exactly two coordinates and `widthMeters: 4`; mapped transverse-road validation runs again on creation, update and approval, including a typed administrator-reviewed agent draft. Imports use the same closure API. Legacy untyped polygons remain supported without pretending they were road-snapped. Omitting an existing explicit type on update preserves it and cannot bypass the stricter validation.

Closure areas use one closed, nonzero-area polygon ring. Crossing edges, repeated adjacent vertices, and holes are rejected; draw separate closure areas when needed. Routing reads every published closure, independently of the state view's display limit, so older active restrictions are not silently omitted.

The red-road snapshot normally uses the graph-edge/polygon intersection helper used by routing, clipping to affected portions so an open junction/remainder is not painted closed. It is active for `startsAt <= at < endsAt`, or indefinitely after an unknown end. It intentionally has no 30-second margin: routing still evaluates actual future traversal with its documented uncertainty margin. Future/expired/draft/cancelled closures are absent from this bright-red snapshot. Each feature names its closure; overlapping different closures may share road geometry. When no supported geometry can be established, no road section is invented; typed contained lines retain the display behavior below.

The map opts into `includeUpcoming=true` to align both red and yellow marker coordinates with the midpoint of an affected road segment. This option reads the same complete published routing snapshot, without truncating older events or imposing a 30-day horizon; the existing bounded geometry-content cache is shared by display and routing. Upcoming roads are not permanently coated: hover or keyboard focus temporarily reveals that marker's affected section in yellow, while click/tap pins it until another tap, an outside click or Escape. Active red lines remain above an overlapping yellow preview. Leaving/ending the schedule or hiding closures clears the preview. Client geometry responses are keyed by visible published IDs/revisions and request mode; aborted or mismatched responses never repaint a newer snapshot. Markers retain MapLibre's positioning classes and use geographic coordinates at every zoom rather than a screen-space offset. When no matched line or valid drawn line is available, only the area's marker remains; no road section is invented.

Explicitly typed road/barrier selections retain their full contained line beyond/across the bundled graph boundary or without that offline graph. Road intervals in that case carry **`unverifiedDrawing: true`**, because a client-supplied type is not persisted proof that it used the mapped-road picker. Inside coverage, road intervals still clip against actual graph roads. Blockades retain their separately validated transverse line. Legacy untyped area restrictions still clip against offline roads; a contained legacy line wholly outside that coverage can also display with the unverified marker. Every displayed segment must be contained by its actual polygon. Non-line/uncontained drawings do not gain invented road strokes. Public moderation/status/selected-time filtering still applies, and stored polygons continue to govern routing. Existing synthetic [32-day test closures](../engineering/LOCAL_TEST_CLOSURES.md) are examples rather than current verified road reports.

## Synthetic demonstrations and commute checks

Demo catalogue entries contain `id`, `title`, `description`, `enabled`, `closureIds`, `coordinates`, `timing`, `startsAt`, and `endsAt`. The original six return contiguous chains of actual named OSM road segments. Four additional scenarios return a single closure centre plus optional `suggestedJourney: {origin: Place, destination: Place}` and `includeInBulk: false`. The UI's **Add defaults** excludes these focused experiments; **Try route** enables the selected event and submits its endpoints through normal `/plan` with no forced stops. Other enabled closures still apply.

Eight scenarios start 30 minutes before the supplied instant and end two hours after it; Aabpara starts 45 minutes after it, and Zero Point ended one hour before it. Schedules are chosen on enable and then remain fixed, so inspecting another map time changes visibility rather than silently moving the closure. `enabled` means the owned record is still published, including when it is future or expired. Disable/re-enable resets that demo's schedule around the supplied instant and reuses its record ID. All demo evidence is explicitly synthetic. [Demo guide](../engineering/DEMOS.md) lists IDs and example workflows.

Enabled commutes are checked after relevant personal saves and by the running local scheduler/worker. Local development supports minute checks; production requires the separately configured private worker/Scheduler, which is not activated by publishing this branch. Alerts appear in the app; **external push, email, SMS, and closed-server notification delivery are not implemented**. Duplicate impacts for the same next occurrence and closure revisions are suppressed. Estimates use the imported OSM graph or online OSRM with ordinary speed assumptions and no live traffic. Graph/provider limitations remain explicit.

## Pakistan routing and online search

`GET /api/places?q=...` awaits local + Pakistan-filtered Photon lookup. Both the provider country code and independent Pakistan coordinate boundary are checked; foreign/mislabeled results are discarded. Up to 160 query characters. Empty/one-character search remains local; typed latitude/longitude suggestions work without this endpoint. An unavailable online lookup with no local result returns a clear service error.

`POST /api/plan` accepts the same GeoJSON-coordinate request and up to five ordered stops. All endpoint/stop coordinates must be within Pakistan. Covered Islamabad requests use local routing; other Pakistan requests await the OSRM adapter. `PlanResponse.source` is `local-osm` or `osrm`; `graphVersion` identifies the actual provider/data snapshot, while `GraphStatus.bounds` still describes only the bundled **local** extract. Provider outages/unverifiable routes return an explicit empty plan with `unavailableReason`. Closure revisions changed during an asynchronous request are rechecked once; repeated concurrent edits return HTTP 409 for a fresh plan. Saved-commute checks also await planning and avoid overlapping background sweeps.

Toll/checkpost POIs, prices and waiting times are not API fields and are not provided. See [routing](ROUTING.md) for online-provider behavior, country-boundary provenance and limitations.

## Profiles, consent and personal trips

This section describes the standalone SQLite profile and retention rules. Firebase modes instead scope personal profiles/records to the verified UID as described above. National saved/consented inferred journey checks send endpoint/stop coordinates to the online router; raw GPS trace arrays are not sent to the search/routing provider.

There is one profile per local SQLite database, shared by browsers opening this installation. It is a preferences record, **not an account, login, identity boundary, or separate person's protected storage**. Its ID is always `local`; defaults are `displayName: Traveller`, `theme: dark`, `mapDetail: clean`, `mapStyle: outdoors` (**Classic**), `browserNotifications: false`, `collectTravelData: false`, `travelDataChoiceMade: false`, `inferFrequentRoutes: false`, and `transport: car`. New Firebase profiles and guest defaults use the same Dark/Classic pair. Missing appearance fields fall back to Dark/Classic; explicit Light/Dark/System and saved map styles, including Night, are preserved. SQLite backfills only missing appearance fields on opening, without changing timestamps; Firestore reads use these fallbacks without writing, and the next profile update retains them. The frontend also starts Dark while loading/missing a preference; explicit System follows OS appearance. Existing guest v1/v2 choices are retained rather than forcibly migrated to Night or reset on every login. Missing collection permission or acknowledgement on an older profile means false. The server controls timestamps. Display names must be 1–60 nonblank characters; optional `city` and `location` remain strings (max 80/120 characters). The UI offers a lazy local **96-city curated alphabetical selection**, preserves unmatched saved values and keeps neighbourhood free text; the API stays compatible with existing strings. Optional `photoDataUrl` uses the raster image validation above, or `""` to remove it. Theme is light/dark/system; map detail clean/standard. Other transport modes are not implemented.

The UI offers **Classic, Minimal and Night**, independently of light/dark appearance and map detail. **Classic (`outdoors`)** is the new-profile/missing-style default, superseding the earlier Night default; existing deliberate style selections remain saved. Legacy `streets`/`contrast` remain accepted for compatibility and render as Classic, without a database migration. Unsupported values return 400 without changing the profile. Header theme/map controls PATCH only their preference and apply only that requested field locally, then reload the current account state; an older full PATCH snapshot cannot restore newer consent or identity fields. See [map styles](../guides/MAP_STYLES.md).

`browserNotifications` records the user's preference; browser notification permission is separate. It does not register a push service or deliver while the app/backend is stopped. Inferred warnings also require collection/learning permission; opting out retains past in-app warning history.

`collectTravelData` is an explicit off-by-default permission. The UI's allow action sets collection and inference true together; inference can then be switched off independently. Enabling inference without collection returns 400. Disabling collection forces inference false, including at the atomic storage update. Trip writes require collection at their storage boundary; learned reads/checks and inferred-alert writes require both flags. Missing permission never authorizes collection. Existing trips/alerts and deliberately saved commutes remain under their retention rules rather than being deleted implicitly.

Optional `travelDataChoiceMade` accepts a strict JSON boolean; strings/numbers/null are rejected. It acknowledges the onboarding choice without authorizing collection, inference or browser location. The registration UI writes `{travelDataChoiceMade:true, collectTravelData:true, inferFrequentRoutes:true}` for Allow and the same acknowledgement with both permission flags false for Not now. Updating acknowledgement alone preserves actual consent. Old accounts are not forced into a prompt merely because the field is absent; prompting also requires the successful-registration marker for the current UID. See [account/profile behavior](../guides/ACCOUNT_AND_PROFILE.md).

Optional `demoData: true` on a profile/trip denotes server-owned provenance for the explicitly seeded [User 123 localhost sample](../engineering/SAMPLE_ACCOUNT.md). `PATCH /api/profile` and `POST /api/trips` reject client-supplied `demoData` as an unknown field. The emulator-only seed writes fictional summaries without raw GPS directly into its fixed private UID; it does not bypass consent for ordinary API trip writes or change other users/shared data. Sample fuel snapshots are fictional and do not replace PSO's shared dated-price cache.

With permission, starting GPS guidance can save meaningful foreground trips from the existing navigation watcher; route preview/planning starts no recording. Stop saves sessions of at least 60 seconds/100 m; hiding the page discards the unsaved navigation fragment, and opt-out/account changes discard it and abort pending saves. Activity is a read-only summary/history workspace and no longer starts a separate manual recording watcher. No background GPS is implemented. Road-discovery contribution is a separate per-trip flag and never adds a road automatically. [Personal travel behavior](PERSONAL_TRAVEL_DATA.md) gives exact sample limits and lifecycle.

The localhost sample account may contain simulated point arrays and summary estimates for exercising history, map replay, export and charts. Their server-owned `demoData:true` provenance remains in the domain/export even when the ordinary profile does not display sample banners. These are not live GPS observations, cannot enable `contributeToRoadDiscovery`, and must not become evidence for a real road or be implicitly migrated to production. Clients cannot set/remove the provenance through trip creation or patch payloads.

The learner considers up to 200 recent trips whose raw points remain within the 30-day window. It requires at least three similar journeys on **three distinct Pakistan Standard Time calendar dates**. Reimporting one day's trip does not create three independent observations. Trips need at least eight fixes with accuracy at most 50 meters, at least 80% usable fixes, at least 500 meters of reliable travel, and endpoints at least 400 meters apart. Journeys shorter than two minutes, longer than four hours, with long interruptions, excessive GPS jumps, or inadequate endpoint coverage are excluded. Grouped journeys must have same-direction endpoints within approximately 250 meters and local departure times within 45 minutes; midnight is handled as a circular clock.

The response contains up to ten strongest proposals, each with representative observed endpoints, a median departure rounded to five minutes, observed weekdays, sample count, and most recent observation. It contains no point arrays or inferred street-address labels. Unobserved weekdays are not silently assumed. IDs are deterministic and anchored to the oldest retained independent observation, so adding newer samples preserves identity; deleting or aging out that anchor can change a proposal's ID. Proposals are computed on demand, not stored as extra copies of GPS history.

Enabled learning checks each qualifying proposal's next observed weekday/time after relevant changes and in the active local scheduler/worker. Internally, one representative **real recorded path** is compared to approved closures at its forecast passage times, with a one-minute uncertainty margin; its raw points remain server-side and are not returned by `/frequent-routes` or sent to an online router. Sparse sections are marked approximate. This historical corridor warning does not certify that a path is legal/routable today. A fresh validated route between the endpoints is still planned separately. Alerts carry `frequentRouteId`, never a fictitious `commuteId`. Saving the proposal as a manually editable commute is optional. Nearby saved commutes are only a duplicate-warning hint: a historical conflict is suppressed only when the matching saved plan already reported that closure at the same revision.

Learning is a conservative heuristic, not evidence that a person will travel on a particular future day. It cannot recognize all routes or replace a deliberately reviewed commute schedule. The inferred endpoints can also fall outside the local road graph; normal routing limitations and unavailable results still apply.

Trip distance excludes segments separated by more than 60 seconds, non-increasing timestamps, accuracy worse than 100 meters, or apparent speed above 65 m/s. Such segments count as gaps and do not become invented straight-line travel. Raw points are removed after 30 days from trip end, leaving `points: []` and the computed summary; the summary is deleted after 90 days. Retention runs on startup, every minute, and when trips/state are read. No trip automatically changes the road graph, and the contribution flag does not upload data anywhere in this local build. SQLite deletion is not a guarantee of forensic erasure from disks or backups.

`GET /api/state` returns up to 2,000 closures, 100 commutes, 200 alerts, 150 notices, and 50 trip summaries. Trip summaries omit raw point arrays and include `pointCount`; fetch a trip by ID for its full trace. These are prototype bounds, not a paginated production API. The private agent drains durable pending revisions through transactional claims rather than rely on the latest-notice UI. A model-reviewed notice alone does not establish a closure: every prepared road or service proposal must pass administrator review, current revision checks and its map validation policy.

## Errors and configuration

Error bodies are `{ "error": "...", "details": "..." }`. Validation and malformed JSON return 400, missing records 404, version conflicts 409, bodies above 4 MB return 413, and incorrect write content types return 415. Unexpected errors return a generic 500 without stack traces or raw post content. Route requests that cannot be satisfied normally return a `PlanResponse` with an unavailable reason instead of a fabricated route.

Standalone configuration: `PORT` defaults to 3001; `HOST` must be `127.0.0.1`; `MANZIL_DATA_DIR` defaults to `data`; optional `MANZIL_DB_PATH` overrides the full database filename. Source collection settings are described in [INGESTION_IMPLEMENTATION.md](../operations/INGESTION_IMPLEMENTATION.md). Keep the database, `.env`, browser state, and personal GPS out of Git.
