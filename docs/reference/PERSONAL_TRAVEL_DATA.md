# Personal profile and trip permission

This feature is developed on `codex/feature-development`. Publishing the branch does not update the deployed website. No existing SQLite database or GPS history is migrated to Firebase.

## What a person sees

- **User profile** summarizes name, email, optional photo, city and neighbourhood. **Edit** opens the fields in the shared secondary panel; Save persists the draft together and Cancel/Close/Escape/outside dismissal discards it. Photo selection alone does not persist an image. City uses the searchable local Pakistan populated-place catalogue; area is optional text. Saving them does not request GPS.
- Photos are selected locally, checked as JPEG/PNG/WebP, resized to at most 512 pixels and re-encoded as JPEG before sending. Canvas re-encoding removes embedded metadata. The encoded result is limited to 150,000 characters; profile photos remain private account records.
- **Personal trip data** is visibly **Off** until the person explicitly allows it. Missing fields on an older profile also mean Off.
- **Allow personal trip data & usual-route alerts** enables trip history and repeated-journey alerts together. Usual-route learning has a separate switch, available only while trip permission is on.
- **Stop collecting trip data** turns off both collection and learning. Existing records remain available in Activity for export or deletion.
- Browser notifications require a separate explicit action and browser permission. In-app alerts remain available independently.

## Optional choice after registration

Successful account creation marks only that new UID as pending in memory/session storage. Once the matching private profile is loaded, the UI asks **Allow personal trip data / Not now** before its first-use tour. Existing sign-ins do not receive a forced prompt just because an older profile lacks acknowledgement. Guests never receive this personal-data prompt.

Either confirmed choice stores `travelDataChoiceMade:true` in the private profile. Allow also sets `collectTravelData:true` and `inferFrequentRoutes:true`; Not now sets both false. Escape follows Not now. Acknowledgement is a strict optional boolean, separate from consent: setting it alone never enables collection or inference. The pending session marker is removed only after the API confirms the matching account's choice. A failed request keeps retry controls visible rather than claiming the preference changed; a lost response can follow a committed write, so retrying either explicit choice is safe. Account changes cannot apply another UID's response.

Granting the preference does not request browser location or start GPS. The person still starts GPS navigation explicitly. Consented qualifying guidance sessions save automatically; Activity has no separate manual recording workflow. Profile keeps the permission near identity setup, with grouped vehicle, appearance/language and journey-alert settings below it. Consent can be changed later; existing stored trips remain available for export/deletion. [Account/profile guide](../guides/ACCOUNT_AND_PROFILE.md).

All these settings open the same secondary panel from compact overview rows. Trip history shares its summary/action component with Activity; opening it does not mount a second recorder or request raw traces. View/Export load the selected authorized detail only, and account changes/unmounts abort or discard late private results.

The localhost [User 123](../engineering/SAMPLE_ACCOUNT.md) preview now contains **simulated GPS-shaped tracks generated from public OSM roads**, with consistent summary distances/timestamps/fuel estimates. No browser/device GPS is captured by this generator. Private Firestore chunks store the points; no generated trace arrays or databases are committed. Server-owned `demoData` provenance remains internal, and exported GeoJSON explicitly declares simulation. Repeated sample banners were removed from profile/statistics/history at the owner's request; sample prices remain fictional, with no fake PSO source link or shared live-data replacement. Collection/inference/browser permissions remain Off. The one-time v2 upgrade preserves all profile edits and consent and changes only exact untouched v1 trip fixtures within raw retention; it never restores deleted/edited samples or rolls history into a new month.

## Weekly and monthly personal statistics

**Personal statistics** opens a separate dialog beside Profile on wide screens and a centered scrollable dialog on smaller screens. The shared statistics component used by Activity also supports **This week / This month**, defaulting to the month. The API retains `{week,month,all}` and adds coordinate-free `daily` aggregates for week/month; each day carries trip/distance/time totals and available saved fuel estimates. Weeks start Monday, months start on the first, and all grouping uses **Asia/Karachi trip departure dates**, including trips that cross midnight. Quiet elapsed days have zero values; future days are not fabricated.

Rounded metric cards present distance, time and trip count. Profile keeps a daily **kilometres travelled** bar chart with exact values under **View daily values**. The second chart is now **Fuel price history**, a Petrol/Diesel PSO reference-price step graph from the application's actual cached dated publications. It is independent of a person's fuel consumption and sample-account historical rates. A known rate carries flat through a period until the next published effective date; future-effective publications are excluded and prices before the earliest cached record remain unavailable. **View price history** exposes exact effective dates/prices and a PSO reference link; stale/error/overdue cache is labelled compactly. Opening the graph does not fetch PSO or invent daily revisions.

Fuel spending/litres still use saved trip estimate snapshots, so unpriced trips do not silently receive an invented price. Activity shows **This week / This month** trip, distance, time and estimated-cost cards without either graph, followed by the existing trip history. Information buttons reveal calculation details on hover, keyboard focus or tap; the small footer records PKT/departure-date/retention context. Missing distance series or fuel-price records produce their own unavailable state. Totals include retained summaries beyond the latest-50 history list, with explicit unpriced-trip and partial-history states.

The read-only component requests only aggregate `/trips/statistics` data and reads cached public price records already present in state. Opening it never starts a location watcher, grants data permission or fetches raw trip traces. Loading/failure/retry states remain distinct from an actual zero-trip period. Viewing a trip's path, export and deletion remain explicit history/Activity actions. Sample-account fictional tracks can populate illustrative private distance/spending aggregates; they never replace the public PSO price series. Charts are not evidence of measured fuel consumption or real-device location testing.

## Foreground collection

Optional vehicle name/type, petrol/diesel and km/litre are private profile preferences, saved separately from identity edits. Saving them does not enable GPS. New consented trips can retain an immutable estimated fuel-cost snapshot using that configured vehicle and applicable dated PSO reference prices. Changes to the profile or global prices never rewrite old trip estimates. Unknown vehicle/history or a price day not covered by a successful check stays unpriced. Weekly/monthly UI summaries expose missing pricing and remain subject to 90-day retention; the backend also supports all-retained aggregates. Deleting a trip also removes its saved cost snapshot. These are estimated consumption costs, not fuel receipts; see [fuel provenance and limits](FUEL_COSTS.md).

`useTravelCapture` receives accurate samples from the existing Navigation GPS watcher. It never starts a watcher of its own. The person must start GPS guidance; planning a route, previewing directions or opening Profile does not start recording. Navigation without personal trip permission uses location for immediate guidance but does not retain those fixes as trip history.

With permission, accurate navigation samples are held in memory. Stopping/leaving guidance saves a session only if it has at least two accepted samples, lasts at least 60 seconds and covers at least 100 metres. Samples require reported accuracy of 60 metres or better, a recent timestamp, valid GeoJSON coordinates and at least four seconds between samples. Gaps longer than two minutes start a new fragment. A session is bounded to 20,000 samples. Navigation trips never opt into future road-discovery contributions automatically.

Hiding the page discards the unsaved navigation fragment and aborts pending saves. Permission withdrawal or account changes also discard/abort. A changed account must start its own GPS session. Browser shutdown or network loss can lose an unsaved session; this is not background or closed-app recording.

Activity no longer offers manual Record/Start/Pause/Finish controls and never starts or stops a GPS watcher. Consented foreground navigation owns automatic trip capture through the existing guidance watcher, avoiding a duplicate Activity watcher. Opening Activity or viewing a saved path cannot create a new trip. Future road-discovery contribution remains a separate per-trip choice; no road is automatically published or made routable.

## Server boundaries and usual routes

The API rejects trip saves without collection permission. Both storage adapters recheck permission at the write boundary; Firestore does so in its transaction. Learned-route reads/checks require **both** collection and inference flags, including after awaited work. Inferred alert writes recheck these flags in their storage operation. Revocation prevents new collection/learning; it does not retroactively delete a trip or alert already committed before revocation.

The inference system needs at least three matching, usable journeys on separate Pakistan dates. **Server-marked simulated trips are excluded before quality filtering**, even when the owner allows collection/learning later. The trip-edit API also rejects enabling road-discovery contribution for a simulated trip. Synthetic examples therefore cannot become observed-path alerts or evidence for adding roads. Saved manual commutes remain independent; the two sample commutes are disabled.

For real trips, inference learns direction, start/end and approximate Pakistan departure time, not home/work labels. Public proposals contain no raw points or trip identifiers. For personal alerts, the server also selects one real observation closest to the usual departure, favouring the latest equally representative day. It preserves that observation's quality-filtered GPS segments and relative timing privately; it never joins different days into an invented path.

Published closure polygons are clipped against those recorded segments. Expected passage time is the next usual departure plus each sample's original offset, with a bounded **60-second margin** on each side. A closure scheduled outside that passage window does not trigger an observed-path warning. A closure on the recorded street can therefore warn even when a fresh planner chooses a different, clear main road. Alerts explicitly say **“Your observed journey may be affected”** and describe a **historical corridor warning**. Segments longer than 300 metres or 60 seconds are marked approximate. Poor/interrupted traces still fail the retained trip-quality gates; this is not live traffic, reliable road-access evidence or proof of the next route a person will drive. One representative observation can miss other historical variants.

Fresh planner checks continue to produce independently validated route/departure options. The historical path never becomes a navigation route or modifies the road graph, and it does not turn a clear planned route into a blocked recommendation. Only endpoints/timing are sent to an optional online planner; raw GPS samples remain server-side. Matching saved-commute closure alerts are deduplicated only for the same event revision; a saved journey that avoids an observed street does not suppress that street's warning. Saved commutes remain an independent, manually selected feature.

Raw samples are retained for 30 days and summaries for 90 days by the existing retention policy. Export/deletion remain available in Activity. Real Firebase modes scope personal records to a verified UID. Standalone development still shares one local database and is not production authentication.

The deployed private worker/Scheduler remains separate deployment work. Do not claim reliable closed-app alerts from this UI addition. No Gemini analysis, cloud speech activation or real-device GPS permission was exercised for this change. Focused automated checks mock browser GPS and verify consent, account changes, cancellation, read-only Activity behavior, image processing and inference gates; final integrated verification is recorded in `IMPLEMENTATION_STATUS.md`.
