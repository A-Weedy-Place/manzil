## Admin flow

1. Open **Control centre > Pipeline**, keep **All posts**, and expand a post.
2. Compare **Original post** with **Gemini analysis**. The worker now prepares a separate private proposal for each traffic event. Older saved interpretations have a **Review on map** action that prepares their proposals from saved extraction without rerunning Gemini.
3. Select **Review on map** for the relevant event. The editor receives its title, reason, original text/summary, source link, source-grounded or clearly labelled AI-proposed PKT start/end, drawing and polygon. Resolved geometry is previewed and focused on the map. Opening or editing this preview has no routing effect.
4. Check missing-field messages. A missing start stays blank. An unknown end stays unknown rather than defaulting to one hour from now; approving an indefinite closure requires explicit acknowledgement. A disruption/congestion/service suspension requires explicit confirmation of an actual road restriction before publishing. Edit the road, width or timing where needed.
5. **Approve and add to map** atomically saves the reviewed published restriction and decision history. **Reject proposal** retains the rejection without creating/changing a closure. Rejected proposals cannot be recreated by reopening the same saved interpretation. Closing the editor leaves the proposal pending.
6. A reopening previews the matched existing incident and has a separate **Approve reopening** action. Approval cancels that incident, retains its history and never creates a new blockade. Unmatched, future-dated, already cancelled or subsequently corrected incidents cannot be cancelled through that proposal.

## Mapping boundaries

Gemini supplies names, not trusted coordinates. Road mapping uses the supplied city, named road and source endpoint/point references; it no longer has an Islamabad city allowlist. Production first geocodes those references within the stated Pakistani city, then uses the bundled or bounded on-demand access-filtered OSM graph. Exact road names and connected named endpoints are still required; a similarly named road in another city cannot be substituted. Precise road points use supported nearby road nodes. If road mapping fails and a source specifies one city and a precise landmark, the existing Pakistan-only place search may supply a uniquely matching **review pin**. A landmark pin is explicitly labelled: it does not establish the extent of a closed road and may need moving to the actual road. City centroids, distant namesakes, ambiguous cities and invented straight corridors are not substituted. Uncached lookup may add geocoder/road-source latency and still fail honestly; no model call or automatic approval is introduced. [Road source, budgets and privacy](ROAD_COVERAGE.md).

Unknown or ambiguous geography remains unplaced, with the extracted text/reason/source still filled. Admins can select the section manually. Times matched independently to the source date/clock prefill directly. A saved model time on the known original publication date may also prefill as an explicitly labelled AI suggestion requiring confirmation. Unknown time basis, missing publication context or unsupported different-day estimates remain blank; unknown expiry is never invented. The app does not invent a blockade from every traffic tweet. Fuel and missing-person classifications retain their existing treatment.

## Persistence and concurrency

`AgentResult.proposals` contains per-event versions, pending/approved/rejected state, partial draft, mapping method, issues, target incident/revision and decision actor/time. It is private admin data, stored in the existing shared result and source-version metadata in SQLite or Firestore. Incomplete proposals are **not closure records**, so they never enter public map/routing snapshots.

`POST /api/agent/notices/:id/prepare` requires `{revision}` and reuses an existing proposal/decision when present. No API key is needed on the public API because it resolves saved extraction rather than invoking Gemini. Preparation checks the source revision and interpretation claim before saving.

`POST /api/agent/notices/:id/review` requires `{noticeRevision,index,version,decision}` plus a complete `draft` for closure/disruption approval. `confirmRestriction:true` is required for ambiguous access/disruption; `confirmUnknownEnd:true` is required for null expiry. Reopening uses the stored target. All routes enforce administrator access, including verified contributors being denied. The transaction rechecks the source, proposal version/pending state and target closure revision before writing the decision, closure and routing revision together. Concurrent/repeated approval yields one change; stale source edits, archive and intervening incident corrections require fresh review. Closure provenance uses the source timestamp when known, otherwise explicitly records an admin-review time rather than presenting collection time as publication.

Admin edits/cancellation in Blockades keep the existing override flag. Already decided proposals retain their history. A new edited source version can have a new proposal but never silently changes the map; administrators must review it again. Bounded geographic repair/retry is described below. A full correction-history browser remains separate work.

## Operations

The live persisted setting was switched to `enabled:true, autoPublish:false` before this implementation. The new worker/service enforces review-only behavior even if a legacy environment or metadata value requests automatic publication. `PATCH /agent/settings` rejects `autoPublish:true`; the operator helper now supports Status, EnableReview and Disable. Do not roll back to an older worker while re-enabling legacy auto-publication settings.

The Gemini key remains worker-only. Preparing old results uses bounded existing geocoding and Firestore operations, not additional Gemini generation. The existing model request/token/image/backoff/allowance controls and source partial-coverage limitations remain in effect. See [model operations](GEMINI_INTEGRATION.md) and [current release evidence](IMPLEMENTATION_STATUS.md).

Operator backfill: `node_modules/.bin/tsx.cmd scripts/prepare-agent-drafts.ts` previews at most ten eligible existing interpretations; add `--apply` to save their private proposals through the same revision-checked repository method. It uses the signed-in gcloud operator token in memory for the fixed project, never reads a model key, calls Gemini, changes source status, or writes a closure. Existing proposals/decisions are skipped. The live backfill result is recorded in implementation status.

## Visible pipeline and manual analysis - 18 October

Control centre opens on Pipeline. The progress board separates collection, waiting/analysis, posts awaiting review and posts with recorded map changes. Awaiting review previously counted only community closure drafts: Gemini proposals live in private result metadata, so the old zero was misleading. The new Review queue combines both sources and returns there after a map decision. Counts cover the latest 150 loaded posts; multiple event drafts count once per post. Stale source versions, archived posts and fully rejected proposals do not count as pending. Failed analysis is shown separately under Needs attention.

Fetch latest posts collects only. Run Gemini now analyses at most two eligible waiting posts, using the private worker and existing daily allowance. If none are waiting, the run button is disabled while completed reviews remain available. Both five-minute schedules still run independently. Refresh results and saved-state polling never invoke Gemini. During an active run, polling updates roughly every four seconds; idle polling is fifteen seconds while the page is visible. Stale/unmounted responses cannot replace newer decisions.

For a demo: Fetch latest posts -> Run Gemini now (if enabled and waiting) -> Review queue -> expand Original post / Gemini analysis / Map outcome -> Review on map -> Approve and add to map or Reject. Missing start/location/expiry fields are explicit. Only approval publishes a routable closure; opening the preview does not. Already analysed posts need review, not another paid generation. A greyed run button can indicate an empty queue, pause, active batch, cooldown or exhausted daily allowance.

New proposals include an Agent work log: saved interpretation, road lookup, landmark fallback when attempted, incident matching, time checks and private draft preparation. This records actual tools, not hidden model reasoning. Saved older proposals may lack a tool log. Unique matching current agent incidents can become update/reopening proposals without requiring Gemini to supply an ID. Ambiguous matches and admin overrides remain protected. The agent cannot freely execute code or write unrestricted database records.

Eligible unresolved mapping with a precise landmark or road plus two endpoints can be retried without Gemini generation. Retry map tools obeys a fifteen-minute cooldown and maximum three mapping attempts. An idle worker sweep handles at most one eligible saved notice per fifteen minutes, latest thirty notices only. Decided proposals remain unchanged; a fingerprint/version transaction rejects concurrent admin decisions or stale refinements, including failed mapping attempts. Vague locations stay for manual input. This is bounded orchestration, not unrestricted autonomous map publication.

## Production manual trigger configuration

Public API: AGENT_WORKER_URL is the exact private Cloud Run origin. Worker: WORKER_MANUAL_SERVICE_ACCOUNT_EMAIL is the API runtime identity in the same project. Grant that identity roles/run.invoker on this worker service only. The worker verifies Google OIDC audience, verified email and job=agent; this identity cannot invoke source/fuel/commute jobs. The Scheduler identity and jobs remain unchanged. The API has no Gemini key or Secret Manager permission.

The public API request timeout is 180 seconds; private dispatch 140 seconds, worker 150 seconds, browser run 170 seconds. Firebase Hosting rewrites have a fixed sixty-second request timeout (https://firebase.google.com/docs/hosting/cloud-run). Therefore the cloud frontend sets public VITE_AGENT_RUN_ORIGIN=https://manzil-api-ld6lwscfya-as.a.run.app in ignored .env.cloud.local. Only /agent/run uses this direct authenticated API path; it verifies project/auth/storage without a token before sending credentials. Existing origin/CORS/host/role checks apply. Other requests retain Hosting pinning. A later rollback must keep the direct API revision compatible with the hosted frontend. Local/emulator modes keep same-origin requests and do not need this value. No new queue service or recurring model workload is introduced.

POST /api/agent/notices/:id/refine requires {revision}; it reuses saved extraction and enforces the same admin/stale-source boundary as prepare. GET agent/status includes execution, canRunHere, processing, backoffUntil and safe runtime stage/progress/check times. Production POST agent/run strictly accepts {} and forwards only {job:agent}; an unconfigured API remains scheduled-only with HTTP 409. Transport failures return a sanitized 503 and ask the admin to refresh saved activity before retrying.
