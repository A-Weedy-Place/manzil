# Vehicle and fuel estimates

Profiles can store an optional car or motorcycle, a label, petrol or diesel, and self-reported **km per litre**. Economy may be blank; no fuel cost is shown until both an economy and an applicable dated price exist. Valid economy is 1–200 km/L. A motorcycle selection describes consumption only: the current road engine still uses its existing car-access profile, so it does not claim motorcycle-specific permissions or shortcuts.

Route cards calculate `distance / 1000 / kmPerLitre × PKR per litre`. These are estimates, separate from travel time. They exclude idling, road conditions, driving style, tolls, maintenance and outlet freight. A future journey uses the latest known applicable reference rate; future prices are not forecast or guaranteed.

## Price source and daily checks

The collector reads the public [Pakistan State Oil POL archive](https://psopk.com/fuel-prices/pol/archives), requiring no account, key or paid API. Its first page contains up to ten dated revision tables. It accepts only **PREMIER EURO 5** for petrol and **HI-CETANE DIESEL EURO 5** for diesel, in `Rs./Litre` tables. LPG, Octane+, E10, aviation products, per-tonne and foreign-currency quotations are excluded. Missing products, invalid dates or units, conflicting same-date prices and malformed numbers fail closed. HTML is capped at 1 MB with a ten-second request timeout and no redirects.

The [PSO current prices page](https://psopk.com/en/fuels/fuel-prices) states these prices exclude freight to the outlet; the final retail bill can differ. The app therefore identifies them as **PSO reference prices (excluding outlet freight)**. The source publishes an effective calendar date without an explicit hour. For calendar lookup, Manzil represents that date as midnight **Asia/Karachi**, an interpretation rather than an independently confirmed transition instant. A missing new daily row does not imply a failed check: one effective rate continues until the next listed revision. `effectiveFrom`, retrieval time and last successful check remain separate.

`FuelService` persists a global `fuel:checkedDay` claim and `fuel:status` in root metadata. SQLite uses a transaction; Firestore uses a transaction across all service instances. Exactly one attempt is allowed per PKT date, including failed attempts and admin checks. A restart catches up once; the next opportunity is the following PKT midnight. Failed checks preserve the last successful rates and expose an error, without substituting a fixture or scraping on route requests. No API, route or profile GET triggers an external check.

Status is `unavailable` before initial coverage, `fresh` after a successful daily check, `stale` after the next daily deadline, or `error` after failure. Cached records can remain usable with stale/error provenance visibly reported. Up to 400 effective records are retained. New first-page records merge only with an overlapping cached archive window. A forward gap after a long offline period resets coverage to the new window; a disconnected older source window is rejected. This prevents a long-unobserved interval from silently inheriting an obsolete price. The app does not backfill the site's 47-page archive or claim complete historical coverage.

Standalone mode starts a daily service poll. Emulator development invokes the existing worker `commutes` job, which includes a coalesced fuel check, and also supports a dedicated `fuel` job. This also works with an already-running earlier launcher that only knows `commutes` and `source`. Automatic external checks are suppressed under `NODE_ENV=test`; tests inject offline price collectors/caches instead. A separately released production worker can receive authenticated `POST /internal/tick` with `{"job":"fuel"}`. No production Scheduler, deployment or live cloud configuration is activated by this feature branch. `POST /api/fuel/check` is an admin action and respects the same daily cap.

## Private trip snapshots and statistics

GPS collection still requires explicit profile consent and existing foreground recording rules. Saving a trip uses its quality-filtered recorded distance, not a route-planner distance. Segments with time gaps over 60 seconds, poor accuracy over 100 m or implausible speed over 65 m/s are excluded just as in the existing distance summary. A valid segment crossing a fuel effective date is divided proportionally by elapsed time. The resulting estimate stores the vehicle/economy, dated rates, provenance, litres, distance and amount on the private trip. It is estimated consumption, **not a receipt or verified actual spending**.

Vehicle changes set a server-managed `vehicleUpdatedAt` only when actual normalized vehicle values change. Routine name/theme/profile saves do not reset it. A new trip receives an estimate only when it started after the current vehicle configuration was set and all its accepted distance has a known applicable price. Its final PKT day must also be covered by a successful check; an old cached route quote cannot establish the fuel price on a new unobserved day. Future-ended trips remain unpriced. Trips spanning a vehicle change or uploaded from before configuration stay unpriced. SQLite and Firestore recheck both consent and current vehicle inside the actual trip-write transaction, so a late profile change cannot attach an obsolete estimate. Trip input cannot supply a `fuelEstimate` or a configuration timestamp. Old trip snapshots are never recalculated when a profile, economy or price cache changes. Unknown historical costs remain unknown.

`GET /api/trips/statistics` reads private summary records without raw GPS and returns `{week, month, all}`. Weeks start Monday and months start on the first, both in PKT; each trip belongs to the period containing its **departure**. `all` means retained history, subject to the existing 90-day trip retention, not lifetime usage. Future-dated or unfinished future trips are excluded. Each period includes priced/unpriced trip counts and unpriced distance alongside estimated PKR/litres. The endpoint examines at most 5,000 summaries; `complete:false` explicitly marks a larger history's partial totals. `/state` still sends the latest 50 trips for ordinary display, rather than reading thousands on every poll.

The latest profile/Activity interface presents **monthly statistics only**, reusing a read-only aggregate component. Personal statistics and Fuel prices open in the shared secondary settings panel beside Profile on wide screens. The API retains all three periods for compatibility. **Checked daily** describes collector frequency, not a promise of daily price revisions. The localhost [User 123 sample](SAMPLE_ACCOUNT.md) has explicitly fictional historical rates/summary costs, labelled separately from the shared PSO cache; its per-trip sample rate never becomes a source hyperlink. See [account/profile guide](ACCOUNT_AND_PROFILE.md).

## API and storage contract

- `LocalProfile.vehicle?: {kind:'car'|'motorcycle', label?:string, fuelType:'petrol'|'diesel', kmPerLitre:number|null}`; optional `vehicleUpdatedAt` is server managed. `transport:'car'` remains the road-engine profile.
- `GET /api/fuel/prices`: public cached `FuelPriceStatus`. `/api/state` also includes it as `fuel`.
- `POST /api/fuel/check` with `{}`: admin only; no arbitrary URLs or injected price body.
- `GET /api/trips/statistics`: signed-in private statistics, before the `/:id` route. Existing trip list/detail responses include optional saved `fuelEstimate`.
- Fuel source metadata is global. Vehicle configuration, trips, GPS and summaries remain private per UID in Firebase modes. Standalone remains one trusted local user, not production authentication.
- JSON fields and root metadata are additive. There are no new packages, API keys, Storage buckets, Firestore rules/indexes or database migrations. Runtime workers need normal outbound HTTPS to PSO. Existing privacy/retention/deletion boundaries remain in force.

## Verification

Focused pure tests cover petrol/diesel/motorcycle consumption, missing/invalid economy and historical prices, future-rate interpretation, effective-date crossing and rejected GPS gaps. Source/service tests cover exact table pairing, malformed/duplicate/conflicting source data, PKT daily claims, concurrent instances, failure caching, SQLite restarts and disconnected history windows. API tests cover public cached access, normalized admin authorization, strict vehicle validation, private statistics, rejected forged costs, immutable saved amounts and atomic vehicle-change races. Real Firebase integration and final build results are recorded in [implementation status](IMPLEMENTATION_STATUS.md).

An independent actual-source smoke check on **17 October 2026** returned ten PSO archive entries, newest effective **16 October** and oldest **3 October**. Its latest petrol/diesel figures were **390.23/396.96 PKR per litre**. These observed source values are documentation evidence, not hardcoded fallback prices. Historical, route and API tests use clearly offline synthetic fixtures; they do not prove exact retail pricing or actual fuel consumption.
